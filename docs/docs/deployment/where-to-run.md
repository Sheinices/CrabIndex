# Где запускать: диск, память, процессор

CrabIndex легко запускается где угодно, но нагрузка сильно зависит от режима. База - это больше миллиона мелких файлов, которые постоянно переписываются, а собственный парсинг с FlareSolverr держит в памяти настоящий браузер. Эта страница помогает выбрать машину и настроить CrabIndex так, чтобы он не мешал остальному.

## Коротко

| Сценарий | Где запускать | Режим базы | FlareSolverr |
| --- | --- | --- | --- |
| Личный поиск для Prisma / Lampa дома | ПК, ноутбук, мини-ПК с SSD | Синхронизация (`--db sync`) | Не нужен |
| Несколько пользователей, свой сервер | VPS или домашний сервер с SSD, работающий круглосуточно | Синхронизация | Не нужен |
| Своя база, парсинг трекеров | VPS с SSD / NVMe, от 2 ядер и 4 ГБ (лучше 4 ядра и 8 ГБ) | Собственный парсинг (`--db parse`) | Нужен для rutracker, kinozal и других за Cloudflare |
| Сервер синхронизации для других установок | VPS или выделенный сервер с NVMe, 4+ ядер, 8-16 ГБ | Собственный парсинг | Нужен |
| NAS или машина с жёстким диском (HDD) | Не рекомендуется | Только синхронизация, с настройками ниже | Нет |

Главное правило: **собственный парсинг и сервер синхронизации держите на VPS или отдельной машине**, а на домашний компьютер ставьте CrabIndex в режиме синхронизации.

## Что нагружает диск

Цифры для полной базы (около 1,3 млн раздач).

| Источник | Что происходит | Сколько |
| --- | --- | --- |
| Файлы базы `Data/fdb` | Около 1,3 млн мелких gzip-файлов (шардов). Каждое изменение раздачи переписывает её шард целиком | 5-6 ГБ данных; на диске больше из-за блоков по 4 КБ; нужен запас inode |
| Индекс `Data/masterDb.bz` | Сохраняется целиком, если база менялась. Задание `jsondb-save` проверяет это каждые 5 минут. Раз в сутки делается копия, копии хранятся 3 дня | Около 60 МБ за раз. При постоянном парсинге это до 15-17 ГБ записи в сутки; копии занимают ещё около 200 МБ |
| Пересчёт статистики | Раз в `timeStatsUpdate` минут (по умолчанию 90) CrabIndex читает все шарды | 5-6 ГБ чтения за раз, несколько минут на медленном диске |
| Журнал изменений `Data/log/fdb.*.log` | При `logFdb: true` на каждое добавление и изменение раздачи пишется строка JSON «было / стало» | С версии 1.0.4 выключен по умолчанию и ограничен 1024 МБ. Если включить (или он включён в старой установке), на сервере с парсингом легко вырастает до гигабайт: на одном таком сервере папка логов заняла 11 ГБ |
| Журналы парсеров `Data/log/*.log` | Строки о каждом проходе трекера | Небольшие, ротация по дням |

В режиме синхронизации записи заметно меньше: меняются только те шарды, которые пришли с сервера синхронизации, парсеров и FlareSolverr нет. Но индекс и статистика работают так же.

## Память и процессор

| Компонент | Процессор | Память |
| --- | --- | --- |
| CrabIndex | 0,5-1 ядро при парсинге, до 2 ядер при пересчёте статистики, в покое почти 0 | 1,5-2,5 ГБ с полной базой (индекс в памяти) |
| FlareSolverr | До 1,5-2 ядер на 10-60 секунд при прохождении проверки Cloudflare | 400 МБ плюс 300-600 МБ на каждый трекер за Cloudflare; установщик ставит лимит 1,5-4 ГБ по памяти сервера |
| cffetch | Почти 0 | 30-60 МБ |

Подробно про FlareSolverr и когда его лучше не ставить - [FlareSolverr и cffetch](../configuration/flaresolverr.md#требования-к-серверу).

## Диск и файловая система

- **Нужен SSD.** На жёстком диске (HDD) миллион мелких файлов превращает каждый пересчёт статистики и каждое сохранение в долгую операцию, а поиск начинает тормозить. Сетевые диски (SMB, NFS) не подходят по той же причине.
- **Запас inode.** Каждый шард - отдельный файл. На ext4 обычно хватает, но на маленьких VPS проверьте: `df -i`. Нужно минимум 1,5 млн свободных inode, лучше с запасом.
- **Место.** Для полной базы закладывайте 10+ ГБ: сама база, индекс с копиями, журналы и запас на рост.
- **Опция `noatime`** при монтировании (по умолчанию `relatime`) убирает лишнюю запись времени доступа при чтении шардов. Необязательно, но полезно.

## Домашний компьютер или ноутбук

Для личного поиска CrabIndex на ПК с SSD - нормальный вариант, если настроить его бережно:

1. **Ставьте в режиме синхронизации** - готовая база приходит с сервера, свой парсинг не идёт:

   ```bash
   sudo bash install.sh --db sync
   ```

   На macOS и Windows пропишите `syncapi: https://sync.crab.rip` в `init.yaml` и не включайте задания парсинга.

2. **Уменьшите лишнюю запись** в `init.yaml`:

   ```yaml
   logFdb: false          # журнал «было / стало» не нужен дома (с 1.0.5 выключен по умолчанию)
   timeStatsUpdate: 360   # пересчитывать статистику раз в 6 часов, а не каждые 90 минут
   ```

   Если журнал изменений нужен, ограничьте его: `logFdbRetentionDays: 3` и `logFdbMaxSizeMb: 500`.

3. **Исключите папку CrabIndex** (особенно `Data/fdb`):
   - из проверки антивирусом в реальном времени (Защитник Windows, другие антивирусы): иначе он проверяет каждый из миллиона файлов при каждом изменении;
   - из облачной синхронизации (OneDrive, Dropbox, iCloud Drive, Яндекс Диск): такую базу нельзя хранить в синхронизируемой папке;
   - из индексации поиска (Windows Search, Spotlight: Системные настройки → Siri и Spotlight → Конфиденциальность);
   - из резервного копирования (Time Machine, История файлов): базу проще заново скачать синхронизацией, чем бэкапить миллион файлов. Сохраните только `init.yaml` и `Data/waf.json`.

4. **Сон и выключение не страшны.** После пробуждения синхронизация догонит пропущенные изменения сама.

## Сервер для парсинга и синхронизации

- VPS с SSD или NVMe, от 2 ядер и 4 ГБ памяти, лучше 4 ядра и 8 ГБ; для сервера синхронизации с FlareSolverr и несколькими трекерами за Cloudflare - 6 ядер и 16 ГБ дают хороший запас.
- Не ставьте на один сервер с другими тяжёлыми сервисами, особенно со своим браузером: две копии Chrome легко съедают весь процессор.
- Следите за журналами: `du -sh Data/log`. Для сервера с парсингом разумно `logFdbRetentionDays: 7` и `logFdbMaxSizeMb: 2000`.
- Раздел **FlareSolverr** в [админ-панели](../admin.md) показывает ошибки обхода Cloudflare по трекерам и подсказывает, какие лимиты поднять.
