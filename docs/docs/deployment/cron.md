# Cron

CrabIndex не запускает парсеры трекеров сам. Их вызывает внешний планировщик (системный cron) по HTTP через обёртку `Data/run-job.sh`. Источник истины для расписания - файл `Data/crontab` в репозитории.

```text
crontab ──► run-job.sh <имя> <URL> <max_time> ──► curl GET ──► /cron/{трекер}/{действие}
```

:::note[Примечание]
Cron не обязателен, если база наполняется синхронизацией (`syncapi`). Встроенные фоновые процессы (сохранение FileDB, статистика, синхронизация) работают без cron - см. [Фоновые процессы](../concepts/background-jobs.md).
:::

## Установка

```bash
crontab /opt/crabindex/Data/crontab          # от имени пользователя сервиса
crontab -l
```

В файле уже прописаны `SHELL=/bin/bash`, `PATH` и базовый адрес `http://127.0.0.1:9117`. Если сервер слушает другой порт или установлен в другой каталог, поправьте пути и адреса.

## run-job.sh

```bash
/opt/crabindex/Data/run-job.sh kinozal-parse http://127.0.0.1:9117/cron/kinozal/parse 900
```

| Аргумент | Описание |
| --- | --- |
| имя | Имя задачи; по нему берётся блокировка `flock` |
| URL | Адрес задачи. В кавычках, если в нём есть `?` или `&` |
| max_time | Общий таймаут `curl`, секунды |

Скрипт:

- берёт блокировку `$LOCK_DIR/<имя>.lock` (по умолчанию `/tmp/crabindex-cron-locks`): если предыдущий запуск той же задачи ещё не завершился, новый пропускается (`SKIP … previous run still active`);
- вызывает `curl` с `--max-time` и таймаутом соединения `CURL_CONNECT_TIMEOUT` (10 с);
- печатает `START` / `DONE` / `TIMEOUT` с кодом ответа и длительностью.

Нужны `bash`, `curl` и `flock`.

## Доступ

Пути `/cron/*` и `/jsondb/*` доступны без ключа только при прямом подключении из локальной сети. Если cron обращается к серверу через обратный прокси или по внешнему адресу, добавьте `devkey`:

```text
http://127.0.0.1:9117/cron/kinozal/parse?devkey=DEVKEY
```

См. [Аутентификация](../authentication.md).

## Типы задач

| Тип | Эндпоинт | Зачем | Ответ |
| --- | --- | --- | --- |
| `parse` | `/cron/{трекер}/parse` | Свежие раздачи (обычно первые страницы) | Выполняется синхронно; журнал работы или `work`, если parse этого трекера уже идёт |
| `UpdateTasksParse` | `/cron/{трекер}/UpdateTasksParse` | Пересчитать карту страниц `Data/temp/{трекер}_taskParse.json` | Сразу `ok` / `work`, работа в фоне (до 30 минут) |
| `ParseAllTask` | `/cron/{трекер}/ParseAllTask` | Полный обход карты страниц | Сразу `ok` / `work`, работа в фоне |
| `ParseLatest` | `/cron/{трекер}/ParseLatest` | Первые страницы всех категорий | Журнал работы или `work` |
| `backfill` | `/cron/{bitru,knaben}/backfill?pages=N` | Постепенный обход архива API с сохранением позиции | Журнал работы |
| `ParseShows` | `/cron/subsplease/ParseShows` | Сезонные паки SubsPlease | Журнал работы |
| `ResumeParseAll` | `/cron/maintenance/ResumeParseAll` | Продолжить незавершённые циклы после рестарта | JSON: какие трекеры запущены |
| `jsondb-save` | `/jsondb/save` | Немедленно сохранить `masterDb` | `ok` / `work` / `syncapi` |
| `cloudflare-warmup` | `/cron/cloudflare/Warmup` | Прогреть сессию FlareSolverr | JSON с `ok`, `host`, `tookSeconds` |
| `maintenance-check` | `/cron/maintenance/Check?mode=report` | Отчёт о целостности FileDB | `ok` / `work`, работа в фоне |

Для фоновых задач `max_time=60` у `run-job.sh` - это только ожидание ответа `ok`/`work`, а не длительность обхода.

### Как работает ParseAllTask

Запрос `ParseAllTask` - это не «перезапустить с нуля»:

- если цикл этого трекера уже идёт - ответ `work`;
- если в текущем цикле остались необработанные страницы - обход продолжается с места остановки;
- если необработанных страниц нет - начинается **новый** круг.

Жёсткого лимита по времени нет: обход идёт до конца карты, до остановки сервера или до 45 минут без прогресса. Частота запуска `ParseAllTask` в crontab определяет, как часто начинается новый круг у трекеров, которые успевают его закончить. `ResumeParseAll` (каждые 15 минут и через ~45 с после старта сервера) только продолжает начатые циклы и новых не начинает.

Ежечасный `parse` не ждёт ParseAll: между страницами архивного обхода ParseAll уступает очередь свежим раздачам.

:::warning[Внимание]
Не запускайте вручную `UpdateTasksParse` и `ParseAllTask` одного трекера одновременно: сервер вернёт `work`, но лишние ручные запуски сбивают расписание.
:::

## Служебные задачи

| Имя | Расписание | max_time | Эндпоинт |
| --- | --- | --- | --- |
| `jsondb-save` | `*/5 * * * *` | 60 | `/jsondb/save` |
| `cloudflare-keepalive` | `5,25,45 * * * *` | 300 | `/cron/cloudflare/Warmup` |
| `cloudflare-warmup` | `55 * * * *` | 300 | `/cron/cloudflare/Warmup` |
| `parseall-resume` | `*/15 * * * *` | 60 | `/cron/maintenance/ResumeParseAll` |
| `maintenance-check` | `0 5 * * 0` | 60 | `/cron/maintenance/Check?mode=report` |

`jsondb-save` - дополнительная страховка: сервер и сам сохраняет изменённый индекс каждые 10 минут.

### API-трекеры

| Трекер | parse | Дополнительно |
| --- | --- | --- |
| bitru | `10,30,50 * * * *` (только свежая страница) | `backfill?pages=20` - `40 * * * *` |
| subsplease | `?pages=2` - `35 * * * *` | `ParseShows` - `25 5 * * *` (max_time 1800) |

## Отладка

```bash
# Запустить задачу вручную и посмотреть ответ
/opt/crabindex/Data/run-job.sh rutor-parse http://127.0.0.1:9117/cron/rutor/parse 900

# Журнал трекера
tail -f /opt/crabindex/Data/log/rutor.log

# Какие фоновые задачи идут сейчас
curl -s http://127.0.0.1:9117/health/background-jobs
```

Каждый запрос `/cron/*` сервер пишет в консоль категории `cron`: путь, длительность и код ответа. Быстрые успешные запросы (быстрее `logging.cronSkipFastMs`, по умолчанию 100 мс) скрыты на уровне Debug.
