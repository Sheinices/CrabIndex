# Фоновые процессы

Часть работы CrabIndex выполняет сам внутри процесса - эти воркеры запускаются автоматически при старте и не требуют настройки cron. Парсинг трекеров, наоборот, запускается **извне** по HTTP (см. [Cron](../deployment/cron.md)).

## Встроенные воркеры

| Воркер | Что делает | Интервал |
| --- | --- | --- |
| Перезагрузка конфига | Проверяет `init.yaml` / `init.conf` и применяет изменения | 10 секунд |
| Индекс FastDB | Перестраивает поисковый индекс «токен названия → бакеты» из `masterDb` | при старте, затем каждые 10 минут |
| FileDB | Сохраняет изменённый `masterDb` в `Data/masterDb.bz`, вытесняет старые бакеты из кеша (`evercache.validHour`) | 10 минут |
| FileDB (быстрый) | Вытесняет наименее читаемые бакеты, если их больше `evercache.maxOpenWriteTask` | 20 секунд |
| Sync: раздачи | Загружает изменения с `syncapi` | через 20 с после старта, затем каждые `timeSync` минут (≥ 20) |
| Sync: сиды/пиры | Обновляет сиды и пиры с `syncapi` (при `syncspidr: true`) | каждые `timeSyncSpidr` минут (≥ 20) |
| Кеш сервера синхронизации | Перестраивает упорядоченный снимок `masterDb` для `/sync/fdb/torrents` | 10 минут |
| Статистика | Обходит FileDB и пишет `Data/temp/stats.json` и `stats-meta.json` | через 20 с после старта, затем каждые `timeStatsUpdate` минут |
| Tracks | Пять задач анализа дорожек и очистка «сирот» в TorrServer (при `tracks: true`) | `tracksinterval.*`, `tracksorphansweepmin` |
| Список трекеров | Собирает рабочие announce-адреса из magnet-ссылок в `wwwroot/trackers.txt` | 1 час; только при `evercache.enable: true` и `evercache.validHour: 0` |
| Возобновление ParseAll | Продолжает незавершённые циклы `ParseAllTask` после рестарта | один раз, через ~45 с после старта |

При `timeStatsUpdate: -1` сбор статистики приостановлен.

## Задачи трекеров

Задачи парсинга запускаются HTTP-запросами `/cron/{трекер}/…`. Длинные задачи выполняются в фоне, а HTTP сразу отвечает одним из статусов:

| Ответ | Значение |
| --- | --- |
| `ok` | Задача запущена (или выполнена) |
| `work` | Такая задача этого трекера уже идёт - новая не запускается |
| `disabled` | Трекер отключён в `disable_trackers` |
| `idle` | (`ResumeParseAll`) продолжать нечего |

Основные типы задач:

| Задача | Что делает | Как выполняется |
| --- | --- | --- |
| `parse` | Свежие раздачи, обычно первые страницы | Синхронно, один экземпляр на трекер (parse-lock) |
| `UpdateTasksParse` | Пересчитывает карту страниц `Data/temp/{трекер}_taskParse.json` | В фоне, лимит 30 минут |
| `ParseAllTask` | Полный обход карты страниц циклами | В фоне; отменяется, если 45 минут нет прогресса |
| `ParseLatest` | Первые страницы каждой категории | Один экземпляр на трекер |

Состояние цикла ParseAll хранится в `Data/temp/{трекер}_parseAllCycle.json`: после рестарта обход продолжается с того же места. Новый круг начинается, только когда в текущем не осталось необработанных страниц. Страница, трижды подряд не загрузившаяся, пропускается (`ParseAll skip slot page=… after 3 failures` в журнале трекера).

Длинные фоновые обходы идут через отдельный экземпляр FlareSolverr (`flaresolverr.crawlUrl`), если он задан, - чтобы не мешать ежечасному `parse`. Между страницами ParseAll уступает очередь `parse` того же трекера.

Подробнее о задачах конкретных трекеров - в [обзоре трекеров](../trackers/overview.mdx) и [Cron API](../api-reference/cron.md).

## Мониторинг

```bash
# Активные ParseAllTask / UpdateTasksParse в этом процессе (публично)
curl http://localhost:9117/health/background-jobs

# Время последнего обновления FileDB (публично)
curl http://localhost:9117/lastupdatedb

# Состояние циклов ParseAll на диске (локальная сеть или devkey)
curl http://localhost:9117/cron/maintenance/ParseAllStatus

# Метки обновления статистики
curl http://localhost:9117/stats/meta
```

Раздел **Задачи** [админ-панели](../admin.md) показывает те же данные, что `/health/background-jobs`, с прогрессом по страницам, а также состояние циклов ParseAll на диске и кнопку «Возобновить ParseAll».

## Остановка

При Ctrl+C или SIGTERM все фоновые задачи получают сигнал отмены. Сервер до 30 секунд ждёт завершения текущих HTTP-запросов, затем сбрасывает изменённые шарды FileDB и `masterDb` на диск.
