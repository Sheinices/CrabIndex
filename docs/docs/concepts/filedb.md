# FileDB

FileDB - встроенное хранилище CrabIndex без СУБД. Раздачи группируются в **бакеты** по названию, каждый бакет - отдельный gzip-сжатый JSON-файл на диске. Индекс всех бакетов (`masterDb`) живёт в памяти. Ни PostgreSQL, ни SQLite, ни Redis не нужны.

## Структура на диске

```text
<рабочий каталог>/
├── init.yaml
└── Data/
    ├── fdb/
    │   ├── 3f/
    │   │   └── a9c1…e07          ← шард (gzip JSON), имя без расширения
    │   ├── b2/
    │   │   └── 44d0…19c
    │   └── …
    ├── masterDb.bz               ← индекс бакетов (gzip JSON)
    ├── masterDb_18-09-2026.bz    ← дневная копия индекса
    ├── temp/                     ← состояние задач, checkpoints, stats.json
    ├── log/
    │   ├── fdb.2026-09-18.log    ← журнал изменений FileDB
    │   └── rutor.log             ← журналы парсеров
    └── tracks/                   ← данные модуля Tracks
```

## Бакеты и ключи

Ключ бакета строится из нормализованного названия и оригинального названия раздачи: `название:оригинальное_название` (если одно из них пустое, подставляется второе). Все раздачи одного фильма или сериала с разных трекеров попадают в один бакет. Внутри бакета записи индексируются по URL раздачи.

Путь к шарду вычисляется из MD5 ключа. Параметр `fdbPathLevels` задаёт раскладку:

| `fdbPathLevels` | Путь | Каталогов первого уровня |
| --- | --- | --- |
| `2` (по умолчанию) | `Data/fdb/{md5[0..2]}/{md5[2..]}` | до 256 |
| любое другое значение | `Data/fdb/{md5[0]}/{md5}` | до 16 |

:::warning[Внимание]
Не меняйте `fdbPathLevels` после наполнения базы: существующие шарды перестанут находиться.
:::

## masterDb

`masterDb` - словарь «ключ бакета → время последнего изменения». При старте сервер загружает его из `Data/masterDb.bz`; если файла нет или он повреждён - из дневной копии за сегодня или вчера. Сервер начинает принимать запросы только после полной загрузки индекса.

Полные данные раздач (название, magnet, размер, файлы) читаются с диска только при обращении к бакету. Без актуального `masterDb.bz` шарды в `Data/fdb/` после рестарта «невидимы»: поиск пуст, в логе индекса `keys=0`.

Из `masterDb` каждые 10 минут строится поисковый индекс **FastDB** (токены названий → ключи бакетов); см. [Фоновые процессы](background-jobs.md).

## Сохранение на диск

- **Шарды** пишутся на диск, когда запись в бакет завершена, или при вытеснении из кеша.
- **`masterDb`** сохраняется фоновым циклом каждые 10 минут, если индекс менялся (в логе категории `fdb`: `masterDb persisted (N keys)`). Заодно создаётся дневная копия `masterDb_ДД-ММ-ГГГГ.bz`, а копия трёхдневной давности удаляется.
- **`GET /jsondb/save`** - немедленный сброс `masterDb` в фоне. Отвечает `ok`, `work` (сохранение уже идёт) или `syncapi` - на инстансе с настроенным `syncapi` эндпоинт ничего не делает, sync-воркер сохраняет индекс сам.
- **Остановка** по SIGTERM / Ctrl+C сбрасывает все изменённые шарды и `masterDb`.

```bash
curl "http://127.0.0.1:9117/jsondb/save"                  # из локальной сети
curl -H "X-Dev-Key: DEVKEY" "https://host/jsondb/save"     # через прокси
```

## Кеш открытых шардов: evercache

Открытые бакеты держатся в памяти, чтобы повторные записи и чтения не шли на диск. Поведение кеша задаёт блок `evercache`:

| Параметр | По умолчанию (код) | В `Data/example.yaml` | Описание |
| --- | --- | --- | --- |
| `evercache.enable` | `true` | `false` | Кешировать бакеты, прочитанные поиском |
| `evercache.validHour` | `1` | `1` | Через сколько часов без чтения бакет вытесняется. `0` - не вытеснять по времени (все бакеты остаются в памяти) |
| `evercache.maxOpenWriteTask` | `2000` | `200` | Если открытых бакетов больше, каждые 20 секунд вытесняются наименее читаемые |
| `evercache.dropCacheTake` | `200` | `200` | Сколько бакетов вытеснять за один проход |

Режим `enable: true` + `validHour: 0` держит всю базу в памяти: поиск не ограничивается `maxreadfile`, и включается воркер, собирающий `wwwroot/trackers.txt`. Требует много RAM.

## Ограничение чтения: maxreadfile

`maxreadfile` (по умолчанию `200`, в шаблоне `250`) - сколько бакетов максимум читает один поисковый запрос при нечётком совпадении по названию. Защищает от чтения тысяч шардов на коротких запросах вроде «the». Ограничение не действует, если включён `evercache` с `validHour: 0`.

## Журнал изменений

При `logFdb: true` каждое добавление или обновление раздачи записывается строкой JSON в `Data/log/fdb.ГГГГ-ММ-ДД.log`.

| Параметр | По умолчанию | Описание |
| --- | --- | --- |
| `logFdb` | `true` | Вести журнал изменений |
| `logFdbRetentionDays` | `7` | Удалять файлы старше N дней (`0` - не удалять) |
| `logFdbMaxSizeMb` | `0` | Общий лимит размера журналов, МБ (`0` - без лимита) |
| `logFdbMaxFiles` | `0` | Лимит числа файлов (`0` - без лимита) |

При массовом импорте (первая синхронизация) журнал быстро растёт - на маленьких дисках выключите его или задайте лимиты.

## Целостность

Проверка и исправление FileDB - через `/cron/maintenance/Check` или команду `crabindex maintain`. См. [Обслуживание FileDB](../operations/maintenance.md).
