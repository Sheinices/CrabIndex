# Синхронизация

Наполнять FileDB можно двумя способами, и их можно сочетать:

| Способ | Как работает | Когда подходит |
| --- | --- | --- |
| **Синхронизация (`syncapi`)** | Встроенный sync-воркер загружает изменения с удалённого сервера по протоколу `/sync/fdb/torrents` | Нужна готовая база без обхода трекеров; нет доступа к трекерам или FlareSolverr |
| **Собственный парсинг** | Внешний cron вызывает `/cron/{трекер}/…`, парсеры обходят трекеры напрямую | Нужна независимость и максимальная свежесть по своим трекерам |

Любой инстанс CrabIndex одновременно может быть и **клиентом** синхронизации (тянуть данные с `syncapi`), и **сервером** (отдавать свою базу другим через `/sync/*`, если `opensync: true`).

## Клиент: загрузка с syncapi

```yaml
syncapi: https://sync.crab.rip
synctrackers:          # какие трекеры принимать; не задано - все
  - rutracker
  - kinozal
  - rutor
syncsport: true        # принимать раздачи категории «спорт»
syncspidr: true        # периодически обновлять сиды/пиры
timeSync: 120          # интервал между циклами, минуты (минимум 20)
timeSyncSpidr: 360     # интервал обновления сидов/пиров, минуты (минимум 20)
saveCheckpointEveryNBatches: 5
```

Sync-воркер работает в два потока.

### Раздачи (torrents)

1. Через ~20 секунд после старта воркер проверяет `{syncapi}/sync/conf` и запрашивает `{syncapi}/sync/fdb/torrents?time=…&start=…` страницами по ~2000 раздач.
2. Раздачи с трекеров не из `synctrackers` и (при `syncsport: false`) спортивные отбрасываются, остальные записываются в FileDB.
3. Пока сервер отвечает `nextread: true`, воркер продолжает. Каждые `saveCheckpointEveryNBatches` страниц (и не реже раза в 5 минут) он сохраняет `masterDb` и позицию.
4. По окончании цикла воркер ждёт `timeSync` минут и начинает снова - уже только с изменений после сохранённой позиции.

Позиция хранится в `Data/temp/lastsync.txt` (последний загруженный бакет) и `Data/temp/starsync.txt` (конец последнего полного прохода). Удалите оба файла, чтобы начать загрузку заново.

### Сиды и пиры (spidr)

При `syncspidr: true` раз в `timeSyncSpidr` минут воркер проходит всю удалённую базу в облегчённом режиме - только `url`, сиды и пиры - и обновляет эти значения у существующих раздач.

:::note[Примечание]
Первая загрузка большой базы занимает часы и заметно нагружает диск. Журнал `logFdb` в это время быстро растёт - см. [Логирование](../configuration/logging.md).
:::

:::note[Примечание]
На инстансе с `syncapi` эндпоинт `/jsondb/save` ничего не делает и отвечает `syncapi`: индекс сохраняет sync-воркер.
:::

### Переименованные записи

Записи старше курсора `start` приходят «тонкими», только сиды, пиры и URL. Если такого URL у клиента нет, значит сервер сменил адрес записи (новый slug или домен) или перенёс её в другой бакет после последнего полного прохода, а полная запись не пришла. Клиент дозапрашивает такой бакет целиком через `/sync/fdb?key=` и импортирует его; число дозапрошенных записей пишется в лог синка. Сервер со своей стороны поднимает `updateTime` при смене URL, поэтому такие случаи редки и остаются в основном после массовых миграций.

### Удаления

Бакет в ответе `/sync/fdb/torrents` отдаётся целиком, поэтому для трекеров из списка `trackers` в `/sync/conf` (то, что сервер парсит и не отключил) его содержимое считается полным. После импорта клиент удаляет у себя записи таких трекеров, которых в пришедшем бакете нет: сервер их удалил, слил как дубли или перенёс в другой бакет после переименования. Записи трекеров, которых сервер не отдаёт (например, клиент парсит их сам), не трогаются. Число удалённых пишется в лог синка рядом с числом добавленных. Сервер старой версии без поля `trackers` удалений не вызывает.

### Сверка целостности

Раз в `timeSyncCheck` минут (по умолчанию сутки; первый раз через час после старта) клиент скачивает список бакетов сервера (`/sync/fdb/digest`) и сравнивает с собственным `masterDb`. Бакеты, которых нет или у которых отличается `fileTime`, докачиваются целиком, лишние удаляются, если состоят только из записей трекеров сервера. После импорта страницы и после докачки бакета клиент записывает себе `fileTime` бакета с сервера, поэтому при следующей сверке совпадающие бакеты совпадают и по метке. Так закрываются все случаи, когда инкрементальный поток что-то пропустил: страница, потерянная на таймауте, переименование, удаление до появления правила удалений. Отчёт виден в разделе **Обзор** (карточка синхронизации), там же кнопка **Сверить**. Сервер ведёт список своих клиентов: раздел **Клиенты** админ-панели.

## Сервер: отдача базы другим

При `opensync: true` (по умолчанию) инстанс отдаёт свою FileDB по публичным эндпоинтам. Как поднять полноценный публичный сервер синхронизации (парсинг всех трекеров, домен, nginx, первичное наполнение) - в разделе [Свой сервер синхронизации](../deployment/sync-server.md).

Эндпоинты:

| Эндпоинт | Назначение |
| --- | --- |
| `GET /sync/conf` | Возможности протокола: `{"fbd": true, "spidr": true, "version": 2, "count": <раздач>}` |
| `GET /sync/fdb/torrents?time=…&start=…&spidr=…` | Страница изменений после метки `time` |
| `GET /sync/fdb?key=…` | Отладка: до 20 бакетов, ключ которых содержит подстроку |

При `opensync: false` эндпоинты данных возвращают пустые ответы (`/sync/conf` при этом продолжает отвечать).

### Протокол /sync/fdb/torrents

| Параметр | Описание |
| --- | --- |
| `time` | Метка времени изменения бакета (`fileTime`). Возвращаются бакеты, изменённые после неё. Для первой загрузки клиент передаёт `-1`. При `time=0` ответ пустой |
| `start` | Метка конца последнего полного прохода клиента. Раздачи, не менявшиеся с этого момента, отдаются в сокращённом виде (только `url`, сиды, пиры). `-1` - отдавать полностью |
| `spidr` | `true` - отдавать все раздачи в сокращённом виде |

Ответ:

```json
{
  "nextread": true,
  "countread": 2014,
  "take": 2000,
  "collections": [
    {
      "Key": "матрица:the matrix",
      "Value": {
        "time": "2026-09-01T12:00:00.0000000Z",
        "fileTime": 134169264000000000,
        "torrents": {
          "https://rutracker.org/forum/viewtopic.php?t=123": { "…": "…" }
        }
      }
    }
  ]
}
```

Повторяйте запрос, подставляя в `time` значение `fileTime` последней коллекции, пока `nextread` равно `true`. Раздачи трекеров из `disable_trackers` сервер не отдаёт.

```bash
curl "http://localhost:9117/sync/conf"
curl "http://localhost:9117/sync/fdb/torrents?time=-1"
```

Полное описание - в справочнике [Синхронизация](../api-reference/sync.md).

## Собственный парсинг

Парсеры запускаются по HTTP внешним планировщиком. Готовое расписание для всех трекеров - `Data/crontab`, обёртка - `Data/run-job.sh`. См. [Cron](../deployment/cron.md) и [Обзор трекеров](../trackers/overview.mdx).

Оба способа можно совмещать: например, получать основную базу с `syncapi`, а один-два трекера с авторизацией парсить самостоятельно.
