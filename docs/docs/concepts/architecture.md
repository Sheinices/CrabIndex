# Архитектура

CrabIndex - один процесс `crabindex` (Rust, tokio, axum). Он хранит раздачи в файловой базе, держит индекс в памяти, выполняет фоновые задачи и отдаёт несколько совместимых поисковых API на одном порту.

```text
                  ┌──────────────────────────────────────────────┐
 Клиенты, сайт,   │  HTTP-конвейер (axum)                        │
 админ-панель ───►│  CORS → сжатие → сеть клиента → OpenAPI/     │
                  │  Swagger → security-заголовки → админ-шлюз → │
                  │  статика → авторизация → нормализация →      │
                  │  маршрутизатор                               │
                  └──────┬──────────────┬──────────────┬─────────┘
                         │              │              │
                  поиск  ▼       cron   ▼      config  ▼
               crab-search     crab-trackers-*   Config API
                    │               │ парсеры
                    ▼               ▼
              индекс FastDB ◄── FileDB (Data/fdb + masterDb) ◄── sync-воркер (crab-ops)
                                    ▲
                        фоновые воркеры: stats, tracks, fdb, trackers.txt
```

## Крейты

Проект - cargo workspace из нескольких крейтов в `crates/`:

| Крейт | Назначение |
| --- | --- |
| `crabindex` | Бинарник: HTTP-сервер, конвейер middleware, безопасность, админ-панель (шлюз, сессии, API), Config API, health, Swagger, запуск воркеров, команды `maintain` и `admin` |
| `crab-core` | Модели, конфигурация и горячая перезагрузка, FileDB, HTTP-клиент с прокси, парсинг, логирование, общие механизмы задач трекеров |
| `crab-cloudflare` | FlareSolverr и cffetch, прогрев Cloudflare-сессий (`/cron/cloudflare/Warmup`) |
| `crab-trackers-a` … `crab-trackers-e` | Парсеры трекеров и их маршруты `/cron/{трекер}/…` |
| `crab-search` | Поиск: Jackett, Torznab, Prowlarr и собственный API, Alloha |
| `crab-tracks` | Модуль Tracks (анализ дорожек через TorrServer) и статистика `/stats/*` |
| `crab-ops` | Синхронизация (`/sync/*` и sync-воркер), `/jsondb/save`, обслуживание FileDB, возобновление ParseAll, dev-утилиты |

Веб-приложения лежат отдельно: сайт - в `web/`, админ-панель - в `admin/` (обе на React + Vite). При сборке они попадают в `wwwroot/` и `wwwroot/admin/`. Контракт API - `web/public/openapi.yaml`.

Подробнее о структуре репозитория - в разделе [Сборка](../development/building.md).

## HTTP-конвейер

Запрос проходит слои в таком порядке (снаружи внутрь):

1. перехват паники → ответ `500 {"error":"internal server error"}`;
2. CORS (любой origin, с credentials);
3. сжатие ответа (gzip, br);
4. определение сети клиента: TCP-адрес, доверенные `X-Forwarded-*` только от loopback;
5. `/openapi.yaml`, `/swagger/v1/swagger.json` и Swagger UI на `/swagger`;
6. security-заголовки (CSP, `X-Frame-Options` и т. д.);
7. шлюз [админ-панели](../admin.md): запросы к `{admin.path}` и `{admin.path}/*` проверяются по токену входа и сессии. Без токена запрос идёт дальше и получает ответ несуществующего маршрута. Запросы API панели переписываются во внутренние маршруты (`/api/v1.0/config`, `/cron/…`, `/dev/…` и т. д.) и помечаются как уже авторизованные;
8. статические файлы из `wwwroot/` (если `web: true`), кроме `wwwroot/admin/`;
9. авторизация по политикам `apikey` / `devkey` и журнал запросов `/cron/`;
10. нормализация: путь и имена query-параметров приводятся к нижнему регистру;
11. маршрутизатор.

Обратите внимание: статика отдаётся **до** авторизации, поэтому файлы из `wwwroot/` (включая `/docs/`) всегда публичны. Исключение - сборка админ-панели `wwwroot/admin/`: её отдаёт только шлюз.

## Поток поиска

1. Клиент вызывает Jackett, Torznab, Prowlarr или собственный API.
2. Слой авторизации применяет политику ApiKeyWhenConfigured.
3. Поисковый слой нормализует параметры: название, оригинальное название, год, категории, сезон и серию. ID вида `tt…` / `kp…` / `tmdb…` разрешаются в названия через Alloha.
4. Индекс FastDB (токены названий → ключи бакетов) выбирает нужные бакеты FileDB, шарды читаются с диска или из кеша.
5. Результаты объединяются по infohash, фильтруются и сортируются.
6. Один и тот же набор отдаётся в формате клиента: Jackett JSON, Torznab XML, Prowlarr JSON или собственный JSON.

Подробнее - [Поиск](search.md).

## Хранение и фоновые задачи

FileDB хранит индекс бакетов в `Data/masterDb.bz`, данные - в шардах под `Data/fdb/`. Встроенные воркеры обновляют индекс поиска, статистику, синхронизацию и Tracks. Парсеры трекеров запускает **внешний** cron через HTTP.

- [FileDB](filedb.md) - как устроено хранилище.
- [Фоновые процессы](background-jobs.md) - что работает внутри процесса.
- [Синхронизация](sync.md) - обмен базой между инстансами.

## Жизненный цикл процесса

При старте сервер:

1. печатает версию сборки;
2. создаёт `Data/fdb`, `Data/temp`, `Data/log`, `Data/tracks`;
3. загружает `init.yaml` (или `init.conf`). Если `admin.token` или `devkey` пусты, генерирует их, записывает в конфиг и выводит в лог адрес админ-панели и `devkey`;
4. полностью загружает `masterDb` - только после этого начинает принимать запросы;
5. регистрирует модули трекеров и запускает фоновые воркеры;
6. слушает `listenip:listenport`.

Команда `crabindex admin` не запускает сервер: она печатает адрес админ-панели и `devkey` из конфига и завершается.

При получении Ctrl+C или SIGTERM сервер отменяет фоновые задачи, до 30 секунд ждёт завершения текущих запросов и сбрасывает на диск изменённые шарды FileDB и `masterDb`.
